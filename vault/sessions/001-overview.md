## 실습 환경이 뭔지

우리가 만들었던 **Moha Cinema 프로젝트에서 DB 스키마와 영화 데이터만 가져왔다.**
앱은 안 가져왔다.

원본 백엔드에는 OAuth, JWT, Security 필터, WebFlux, MyBatis, 추천 서비스가
얽혀 있다. 부하를 걸면 응답 시간에 그게 전부 섞여서
**"쿼리가 느린 건지 다른 게 느린 건지" 구분이 안 된다.**
그래서 병목을 하나만 만들어두려고 파일 5개짜리 앱을 새로 짰다.

```
  [ k6 ]                    부하를 만든다. 초당 몇 건씩 요청을 던진다
    │
    │  HTTP
    ▼
  [ Spring Boot ]  :8080    파일 5개. Security 없음, 캐시 없음
    │                       컨트롤러가 리포지토리를 직접 부른다
    │  JDBC (HikariCP 커넥션 풀 10개)
    ▼
  [ PostgreSQL ]   :5433    CPU 2개, 메모리 2GB로 제한
                            실습 전용. 개발 DB 아님

  옆에서 지켜보는 쪽
  [ Prometheus ] :9090  ──  5초마다 앱과 DB 상태를 긁어간다
  [ Grafana ]    :3000  ──  그걸 그래프로 그린다
```

k6도 앱도 DB도 **전부 이 노트북 한 대**에서 돈다.

## 데이터 규모

| 테이블 | 건수 | 뭐가 들어있나 |
|---|---|---|
| `movies` | 19,701 | TMDB **실제 영화 데이터**. 제목·감독·개봉일 |
| `genres` | 19 | 드라마, 액션, 코미디 … |
| `movie_genres` | 47,104 | 영화-장르 연결 |
| `user_rating` | **5,030,000** | **우리가 생성한 데이터**. 유저가 영화에 매긴 1~10점 |

영화는 진짜 데이터를 쓴다. `title = '스트립퍼 배심원'`이 나오는 게
`title = 'random text 847293'`보다 디버깅이 훨씬 쉽다.

평점 500만 건은 원본에 583건뿐이라 우리가 만들어 넣었다.
**그런데 일부러 치우치게 만들었다.**

| 유저 | 인원 | 1인당 평점 | 합계 |
|---|---|---|---|
| 헤비 | 100명 | 5,000건 | 50만 |
| 중간 | 1만 명 | 300건 | 300만 |
| 라이트 | 9만 명 | 17건 | 153만 |

영화 쪽도 치우쳐 있다 — **인기 영화 200편에 전체 평점의 40%**가 몰려 있고
나머지 19,501편이 60%를 나눠 갖는다.

> **왜 치우치게 만들었나:** 균등하게 넣으면 누구를 조회하든 건수가 같아져서
> "조회 대상에 따라 DB가 다르게 동작한다"는 걸 아예 볼 수 없다. 오늘 실험의 절반이 죽는다.

## API 4개 — 각각 뭐 하는 건지

앱에는 조회 API만 있다. 쓰기는 없다.

| 엔드포인트 | 하는 일 | 왜 만들었나 |
|---|---|---|
| `GET /lab/movies?offset=&limit=` | 영화 목록을 `movie_id` 순으로, 앞에서 `offset`개 건너뛰고 `limit`개 | 오프셋 페이징 (A-2 비교군) |
| `GET /lab/movies?cursorId=&limit=` | 같은 목록인데 `movie_id > cursorId`부터 `limit`개 | 커서 페이징 (A-2 개선안) |
| `GET /lab/ratings?userId=&from=&to=` | 한 유저가 그 기간에 매긴 평점 전부. `updated_at` 최신순 | 복합 인덱스·선택도 실험 |
| `GET /lab/movies/{id}/stats` | 그 영화 평점의 **개수와 평균을 매번 센다** | count 집계 vs 미리 집계 (A-2 ⑦) |

`/lab/ratings`는 `offset`·`cursorUpdatedAt`도 받는다. A-1과 A-2에서 쓰는 형태다.

```
GET /lab/ratings?offset=4900000&limit=10                      <- 오늘 제일 느린 요청
GET /lab/ratings?cursorUpdatedAt=2024-10-01T00:00:00Z&limit=10  <- 그 개선안
```

두 가지를 일부러 뺐다.

- **`userId`는 로그인 토큰이 아니라 쿼리 파라미터로 받는다.** 인증이 응답 시간에 끼어들 여지를 없앴다.
- **캐시가 없다.** 두 번째 요청이 빨라지면 뭘 재는지 알 수 없다.

## 화면 보는 법

### Grafana — "A-1 한 화면" 패널 4개

| 패널 | 뭘 보여주나 |
|---|---|
| 1. TPS | 초당 몇 건을 실제로 처리했나. **부하를 올려도 이게 안 오르면 거기가 한계** |
| 2. p95 응답시간 | 100건 중 95번째로 느린 요청. 평균은 안 본다 — 일부만 느린 걸 평균이 뭉갠다 |
| 3. `pending` | **DB 커넥션을 못 얻어 줄 서 있는 스레드 수.** 0보다 크면 대기가 생긴 것 |
| 4. DB CPU | DB 컨테이너 CPU. **200%가 상한**(코어 2개). 여기 붙으면 DB가 한계 |

부하가 없을 땐 3·4번이 바닥에 평평하다. 그게 정상이다.

### EXPLAIN 출력 — 세 줄만 본다

```
 Bitmap Heap Scan on user_rating  (cost=...) (actual time=... rows=10339 loops=1)   <- ①
   Filter: ((user_id >= 1) AND (user_id <= 100))
   Rows Removed by Filter: 4215000                                                  <- ②
 Planning Time: 0.232 ms
 Execution Time: 240.519 ms                                                         <- ③
```

| | 뭘 보나 |
|---|---|
| ① 맨 윗줄 스캔 방식 | `Index Scan` / `Bitmap Heap Scan` / `Seq Scan` 중 뭔가. **오늘 B급의 전부가 이거다** |
| ② `Rows Removed by Filter` | 읽어놓고 버린 행 수. 크면 헛일을 많이 했다는 뜻 |
| ③ `Execution Time` | 실제 걸린 시간 |

**나머지 줄(`cost`, `Heap Blocks`, `Planning Time`, `JIT`)은 오늘 안 본다.**
궁금하면 물어보되, 오늘 판단 근거로는 안 쓴다.

## 오늘 순서와 왜 이 순서인지

| 순서 | 내용 | 책 |
|---|---|---|
| 1 | **B급 4개** — 쿼리 하나씩 EXPLAIN | 3장 |
| 2 | **A-1** — 부하 걸고 서버 전체 보기 | 2장 |
| 3 | **A-2** — 찾은 병목 고쳐보기 | 3장 |

**책 순서(2장 → 3장)가 아니라 난이도 순이다.**

B급은 쿼리 한 번 치면 결과가 바로 나온다. 변수가 하나뿐이라 인과가 명확하다.
A-1은 부하를 4분씩 걸어야 하고, 앱·커넥션 풀·DB CPU가 동시에 움직여서
"뭐 때문에 느린지"를 골라내야 한다.

**쉬운 것부터 해서 `EXPLAIN` 읽는 눈을 먼저 만들고 부하 실험으로 간다.**

## 오늘의 합의

시작하기 전에 세 가지를 못 박고 간다.

**1. 절대값은 안 믿는다. 상대 비교만 본다.**
k6와 앱과 DB가 한 노트북에서 CPU를 나눠 쓴다.
"우리 서버 몇 TPS"는 의미 없다. **"조건을 바꿨더니 어느 쪽으로 움직였나"만 본다.**

**2. 배수는 인용하지 않는다.**
같은 실험을 이틀에 걸쳐 재봤더니 1,788배가 128배로 바뀌었다(OS 캐시 상태 때문).
**"빨라진다 / 느려진다 / 안 변한다"** 방향만 말한다.

**3. 예측은 반드시 글로 적는다.**
머릿속으로만 하면 결과를 보고 "아 그럴 줄 알았어"가 된다.
**예측이 틀리는 순간이 오늘 배우는 유일한 지점이다.** 틀리라고 적는 것이다.
