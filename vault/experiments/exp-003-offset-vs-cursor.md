## 가설

깊은 오프셋 조회(`OFFSET 4900000`)는 건너뛸 행을 전부 읽어야 하므로 느리다.
커서 조회(`WHERE updated_at < ?`)는 시작 위치를 바로 찾으므로 깊이와 무관하게 빠르다.

## 조건
- 앱: Spring Boot 3.5.5, 호스트에서 실행
- DB: PostgreSQL 16, CPU 2 / mem 2g
- 데이터: `user_rating` 5,030,000건. `updated_at`은 2024-08-28 ~ 2026-08-29에 분포
- 대상
  - 오프셋: `GET /lab/ratings?offset=4900000&limit=10`
  - 커서: `GET /lab/ratings?cursorUpdatedAt=...&limit=10`
- 변수: **`CREATE INDEX ... ON user_rating(updated_at DESC)` 유무**
- 두 방식 모두 정렬 기준은 `updated_at`이다

## 결과
원본: [[2026-08-30_exp-001_session_results]] A-2

| 방식 | 인덱스 없음 | 인덱스 있음 | 방향 |
|---|---|---|---|
| 오프셋 | 2.97초 | 12.99초 | **나빠짐** |
| 커서 | 0.29초 | 0.014초 | 좋아짐 |

같은 인덱스 하나를 걸었는데 두 방식이 **반대로** 움직였다.

인덱스가 있는 상태에서 두 방식의 차이는 12.99초 vs 0.014초다.
인덱스가 없을 때의 차이(2.97초 vs 0.29초)보다 오히려 벌어졌다.

## 예측과의 차이
> 이 노트에서 가장 중요한 섹션.
> 무엇을 틀렸고, 왜 틀렸는가.

## 남은 질문
- #question 인덱스를 걸었더니 오프셋이 왜 느려졌는가.
  옵티마이저가 순차 스캔 + 정렬에서 인덱스 스캔으로 계획을 바꾸면서
  490만 건을 인덱스로 훑고 매 건 테이블을 찾아가게 된 것으로 보이는데,
  **당일에 `EXPLAIN`을 안 찍어서 확인하지 못했다.** #가설
- #question 이 현상은 책에 없다. 책은 "오프셋 대신 ID 기준으로 조회하라"고만 한다.
  인덱스를 걸면 오프셋이 더 나빠진다는 것은 어디까지 일반적인가
- #question 운영 중이라면 이 인덱스를 걸어야 하나 말아야 하나.
  커서 API는 20배 빨라지고 오프셋 API는 4배 느려진다면 무엇을 기준으로 정하는가

## 이번에 물어본 것
- `OFFSET`이 실제로 어떻게 동작하는가. 건너뛰는 행도 읽는가
- 인덱스가 있는데 옵티마이저가 안 쓰기로 하는 경우가 있는가

## 다음에 할 것

**이 실험은 `EXPLAIN` 없이 시간만 쟀다.** 위 첫 번째 질문에 답하려면
네 조건(오프셋·커서 × 인덱스 유무) 각각에서 `EXPLAIN ANALYZE`를 찍어
실행계획이 실제로 바뀌었는지 확인해야 한다. 다음 회차 첫 15분 후보다.
