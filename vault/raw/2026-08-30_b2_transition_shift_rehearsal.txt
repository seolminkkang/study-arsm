B-2 전환점 재측정 — 2026-08-30, 리허설(한 대)
계기: B-1을 돌린 뒤 B-2를 하니 전환점이 16.2%(2026-08-28 측정)가 아니었다.
조건: PostgreSQL 16 (cpus:2, mem 2g), user_rating 5,030,000
     인덱스: idx_user_rating__movie_rating, idx_user_rating__user_updated
     직전 커밋: 01eaed0

================================================================
0. 측정 중 발견한 오염 요인 두 가지 (먼저 기록)
================================================================

--- (1) autovacuum이 돌면 같은 쿼리 계획이 실행마다 뒤집힌다 ---

B-1 직후 측정을 시작했더니 N=100(약 10%)이 실행할 때마다 달랐다.

  1차 시도: N=100 -> Seq Scan
  2차 시도: N=100 -> Bitmap Heap Scan
  3차 시도: N=200 -> Bitmap, 직후 다시 N=200 -> Seq Scan

원인:
$ SELECT pid, state, query FROM pg_stat_activity WHERE query ILIKE '%vacuum%';
 2934 | active | autovacuum: VACUUM ANALYZE public.user_rating

B-1의 UPDATE 5030000 이 죽은 튜플 500만 개를 만들었고 autovacuum이 뒤따라
돌면서 통계가 계속 갱신됐다. 경계 근처라 통계가 조금만 바뀌어도 계획이 뒤집힌다.
-> autovacuum이 끝난 뒤(pg_stat_activity가 비고) ANALYZE 한 번 하고 재측정함.

--- (2) DROP COLUMN 은 컬럼을 실제로 지우지 않는다 ---

$ SELECT attname, attnum, attisdropped FROM pg_attribute
  WHERE attrelid='user_rating'::regclass AND attnum > 0;

 user_id                      | 1 | f
 movie_id                     | 2 | f
 rating                       | 3 | f
 created_at                   | 4 | f
 updated_at                   | 5 | f
 ........pg.dropped.6........ | 6 | t
 ........pg.dropped.7........ | 7 | t
 movie_id_str                 | 8 | f

지운 컬럼은 `........pg.dropped.N........` 로 자리만 남는다(6, 7번).
그리고 99_cleanup.sql 을 돌린 뒤에도 물리 크기는 줄지 않는다.

================================================================
1. 물리 크기 — B-1이 테이블을 2배로 부풀린다
================================================================

B-1 직후 (99_cleanup.sql 로 컬럼을 지운 뒤에도):
  pg_relation_size  735 MB
  relpages          94,019

VACUUM FULL user_rating; 실행 (5.63초):
  pg_relation_size  327 MB
  relpages          41,917

원인: B-1의 `UPDATE user_rating SET movie_id_str = movie_id::text` 가
5,030,000행을 전부 새로 쓴다. 원본 행은 죽은 튜플로 남는다.
일반 VACUUM은 그 공간을 "재사용 가능"으로 표시할 뿐 파일을 줄이지 않는다.
VACUUM FULL 이 테이블을 통째로 다시 써야 회수된다.

SELECT * 의 width:
  movie_id_str 있을 때  39
  없을 때(명시 컬럼)    34

$ EXPLAIN SELECT * FROM user_rating WHERE user_id BETWEEN 1 AND N;

  N=150   ->  Bitmap Heap Scan

전환점: 약 10.5% ~ 10.8%

================================================================
4. 요약 — 같은 데이터, 같은 인덱스인데 전환점이 3배 넘게 다르다
================================================================

| 상태 | 테이블 크기 | 페이지 수 | 전환점 |
|---|---|---|---|
| 2026-08-28 최초 측정 (부분 부풀림) | 미기록 | 미기록 | 15.9% ~ 16.2% |
| 상태 A: B-1 직후 (부풀림 + 컬럼 있음) | 735 MB | 94,019 | 10.5% ~ 10.8% |
| 상태 B: VACUUM FULL 후 | 327 MB | 41,917 | 33.2% ~ 36.2% |

행 건수도, 인덱스도, 쿼리도 똑같다. 바뀐 것은 테이블의 물리 상태뿐이다.

해석(가설, 비용 모델 직접 확인 안 함): 테이블이 부풀면 같은 행 수가 더 많은
페이지에 흩어진다. 인덱스 스캔은 찾은 행마다 힙 페이지를 찾아가므로
페이지가 흩어질수록 비싸진다. 순차 스캔도 비싸지지만 상대적으로 덜 손해라,
옵티마이저가 더 낮은 비율에서 인덱스를 포기한다.

실습에 주는 함의:
- B-2를 하기 전에 B-1의 흔적(부풀림)을 반드시 걷어내야 한다.
  99_cleanup.sql 만으로는 부족하고 VACUUM FULL 이 필요하다(5.6초).
- 또는 B-2를 B-1보다 먼저 한다.
- 전환점 숫자 자체를 외우게 하면 안 된다. 환경에 따라 10%도 되고 36%도 된다.

================================================================
5. 추가 — VACUUM FULL 후에는 Index Scan이 나오는 지점도 달라졌다
================================================================

깨끗한 상태(327 MB)에서 낮은 비율 쪽을 다시 확인.

$ EXPLAIN SELECT * FROM user_rating WHERE ...

  user_id = 46401         17행       0.000%  Index Scan using idx_user_rating__user_updated
  user_id = 36          5,000행      0.099%  Bitmap Heap Scan
  user_id BETWEEN 1 AND 5   25,000행 0.497%  Bitmap Heap Scan
  user_id BETWEEN 1 AND 10  50,000행 0.994%  Bitmap Heap Scan

2026-08-29 측정에서는 user_id=36(헤비)이 Index Scan이었는데
VACUUM FULL 후에는 Bitmap Heap Scan으로 바뀌었다.

VACUUM FULL이 테이블을 물리적으로 다시 쓰면서 행 배치가 달라진 영향으로 보인다
(#가설). 시딩이 user_id 순서로 INSERT했으므로 다시 쓰면 한 유저의 행이
연속된 페이지에 모이고, 그러면 비트맵 스캔이 유리해진다.

실습에 주는 함의: 3단계 대비를 보여주려면 라이트 유저(46401, 17행)를 써야
Index Scan이 나온다. 헤비 유저(36)는 이제 Bitmap 쪽이다.
-> 001-cheatsheet.md 의 B-2 명령을 46401 / 36 / 4000 / 4500 네 개로 교체함.

================================================================
6. 같은 날 오후 재측정 — 같은 크기인데 경계 선택이 뒤집혔다
================================================================

오전 측정(위 3~5번) 이후 한 일: B-1을 한 번 돌렸다가 99_cleanup + VACUUM FULL로
원복. 테이블 크기는 367 MB로 같다.

--- BETWEEN 1 AND 4500 (1,820,000행, 36.18%) ---

오전 (5회 연속, 전부 동일):
  Bitmap Heap Scan  cost=46366.52..120563.96 rows=1812496 width=34   <- 선택
  Seq Scan          cost=    0.00..122459.40                          (강제 시)

오후 (3회 연속, 전부 동일):
  Seq Scan          cost=    0.00..122461.05 rows=1842369 width=34   <- 선택
  Bitmap Heap Scan  cost=47128.71..121774.25 rows=1842369 width=34   (강제 시)

오후에는 강제로 재본 Bitmap(121,774)이 선택된 Seq(122,461)보다 오히려 싸다.
enable_seqscan=off 로 잰 값이라 다른 경로 비교가 섞였을 수 있어 단정하지 않는다(#가설).
확실한 것은 두 계획의 총비용이 1% 안쪽으로 붙어 있다는 것.

--- 한 자리에서의 안정성 (같은 세션 연속 반복) ---

  BETWEEN 1 AND 4000  ->  Bitmap Heap Scan  3/3 동일
  BETWEEN 1 AND 4500  ->  Seq Scan          3/3 동일 (오후 기준)
  BETWEEN 1 AND 4600  ->  Seq Scan          5/5 동일
  user_id = 46401     ->  Index Scan        3/3 동일
  user_id = 36        ->  Bitmap Heap Scan  3/3 동일

한 자리에서 연속으로 치면 흔들리지 않는다.
흔들리는 건 통계가 바뀌는 순간(autovacuum 진행 중, 테이블 변경 직후)이다.

--- "확실히 Seq Scan"인 값 찾기 (각 3회) ---

  N=5000    1,970,000행  39.2%  [Seq][Seq][Seq]
  N=8000    2,870,000행  57.1%  [Seq][Seq][Seq]
  N=20000   3,668,300행  72.9%  [Seq][Seq][Seq]
  N=50000   4,178,300행  83.1%  [Seq][Seq][Seq]
  N=90000   4,858,300행  96.6%  [Seq][Seq][Seq]

-> B-2 4단계 값으로 8000(57.1%)을 채택. 5000도 안정적이지만 경계(4500)와
   가까워서 여유를 뒀다.

7. B-1 비교 조건 수정 검증
================================================================

기존 안은 ①이 단일 테이블 조회, ②가 조인이라 조건이 두 개 달랐다.
둘 다 조인으로 맞추고 타입만 변수로 남겨 재측정.

--- ① 타입 같음 (bigint : bigint) ---
EXPLAIN ANALYZE SELECT r.* FROM user_rating r JOIN movies m
ON r.movie_id = m.movie_id WHERE m.movie_id = 60300;

 Nested Loop  (cost=6.67..986.19 rows=252 width=39) (actual time=91.920..230.595 rows=10339 loops=1)
   ->  Index Only Scan using movies_pkey on movies m (actual time=0.611..0.616 rows=1 loops=1)
         Index Cond: (movie_id = 60300)
         Heap Fetches: 0
   ->  Bitmap Heap Scan on user_rating r (actual time=91.304..228.951 rows=10339 loops=1)
         Recheck Cond: (movie_id = 60300)
         Heap Blocks: exact=18711
         ->  Bitmap Index Scan on idx_user_rating__movie_rating (actual time=4.943..4.943 rows=20678 loops=1)
               Index Cond: (movie_id = 60300)
 Planning Time: 2.970 ms

--- ② 타입 다름 (varchar->int : bigint) ---
EXPLAIN ANALYZE SELECT r.* FROM user_rating r JOIN movies m
ON r.movie_id_str::int = m.movie_id WHERE m.movie_id = 60300;

 Nested Loop  (cost=1000.29..139415.47 rows=25215 width=39) (actual time=167.168..472.742 rows=10339 loops=1)
   ->  Index Only Scan using movies_pkey on movies m (actual time=0.075..0.079 rows=1 loops=1)
         Index Cond: (movie_id = 60300)
         Heap Fetches: 0
   ->  Gather (actual time=167.089..471.693 rows=10339 loops=1)
         Workers Planned: 2
         Workers Launched: 2
         ->  Parallel Seq Scan on user_rating r (actual time=156.693..455.888 rows=3446 loops=3)
               Filter: ((movie_id_str)::integer = 60300)
               Rows Removed by Filter: 1673220
 Planning Time: 1.177 ms

관찰: 조인 형태가 같아졌으므로 차이는 조인 칼럼 타입 하나뿐이다.
①은 인덱스를 타고, ②는 Parallel Seq Scan + 행마다 캐스팅.
Execution 230ms vs 472ms (배수는 인용하지 않는다 — 캐시 상태에 좌우됨).

측정 후 99_cleanup.sql + VACUUM FULL + 04_indexes.sql 로 367MB 복구 확인.
