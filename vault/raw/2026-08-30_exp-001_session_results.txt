================================================================
B급 — EXPLAIN 한 번으로 끝나는 것
================================================================

--- B-1. 타입이 다른 칼럼 조인 ---

int : int
  Bitmap Index Scan
  529 ms

varchar::int  (movie_id_str 칼럼을 만들어 조인)
  Parallel Seq Scan
  527 ms
  Rows Removed by Filter: 1673220   <- 워커당. 워커 3개 합쳐 약 500만

관찰: 실행 시간은 529ms vs 527ms로 사실상 같다.
차이는 시간이 아니라 읽고 버린 양이다. varchar 쪽은 500만 행을 전부 읽고
조건에 안 맞는 것을 버렸다. int 쪽은 인덱스로 필요한 것만 찾았다.
이 데이터 크기와 이 기계에서는 시간 차이로 드러나지 않았다.


--- B-2. 선택도 ---

user_id = 46401      (17건, 전체의 0.0003%)   Index Scan
user_id = 36         (5,000건, 전체의 0.1%)   Bitmap Heap Scan
user_id BETWEEN 1 AND 100  (약 10%)           Seq Scan

전환점(Bitmap Heap Scan -> Seq Scan으로 바뀌는 비율)이 세션마다 달랐다.

  2026-08-28 리허설                16.2%
  2026-08-30 리허설(테이블 부풀림)  10%
  2026-08-30 당일                  36%

같은 쿼리, 같은 데이터 건수인데 경계가 움직였다.


--- B-3. 커버링 인덱스 ---

전제: VACUUM user_rating 실행 후 측정.

SELECT movie_id, rating FROM user_rating WHERE movie_id = 60300;
  Index Only Scan using idx_user_rating__movie_rating
  Heap Fetches: 0
  0.77 ms

SELECT movie_id, rating, updated_at FROM user_rating WHERE movie_id = 60300;
  Bitmap Heap Scan
  Heap Blocks: 9310
  16.4 ms

관찰: 조회 칼럼에 updated_at 하나를 더했을 뿐인데 실행계획이 바뀌었다.
updated_at이 인덱스에 없어서 테이블 블록 9,310개를 읽으러 갔다.
배율은 인용하지 않는다 — 08-28에 1,788배, 08-29에 128배, 오늘 21배가 나왔다.
비커버링 쪽이 OS 페이지 캐시 상태에 따라 요동친다.
안정적인 것은 Heap Fetches: 0 과 Heap Blocks: 9310 의 대비다.


--- B-4. 복합 인덱스 컬럼 순서 ---

쿼리 A (Q_ordered): WHERE user_id = 36 AND updated_at >= '2026-01-01'
                    ORDER BY updated_at DESC LIMIT 100
쿼리 B (Q_plain):   WHERE user_id = 36 AND updated_at >= '2026-01-01'   (정렬·LIMIT 없음)

인덱스 상태                        쿼리 A                    쿼리 B
--------------------------------- ------------------------- ---------------------------
① (user_id, updated_at DESC)      Index Scan   0.27 ms      Bitmap Heap Scan  1.8 ms
② (updated_at DESC, user_id)      Index Scan   2.9 ms       Parallel Seq Scan 113 ms
                                                            Rows Removed by Filter: 1675371

관찰: 같은 두 칼럼, 순서만 뒤집었다.
쿼리 A에서는 0.27ms vs 2.9ms로 차이가 작다.
쿼리 B에서는 1.8ms vs 113ms로 벌어졌고 실행계획도 인덱스에서 순차 스캔으로 바뀌었다.
차이의 크기를 정한 것은 인덱스가 아니라 쿼리 모양이다.

================================================================
A-1. 커넥션 풀 크기
================================================================

무거운 쿼리 /lab/ratings?offset=4900000&limit=10 에 부하를 걸었다.
도착률 4 rps. 풀 크기는 application.yml에서 바꾸고 앱을 재시작했다.

                      풀 10        풀 50
--------------------- ------------ ------------
처리량                1.2616 TPS   1.2567 TPS
실패율                97.94%       99.70%
p95 응답시간          30 초        30 초
VU 최대               84           84
dropped_iterations    50           51

산술 모델 예측 (최대 TPS = 풀 크기 / 쿼리 실행 시간, 단건 1.16초 기준)
  풀 10 -> 10 / 1.16 = 8.6 TPS

실측 1.26 TPS. 예측의 약 1/7이다.

관찰:
- 풀을 5배 키웠는데 처리량이 1.2616 -> 1.2567로 움직이지 않았다.
- 오히려 실패율이 97.94% -> 99.70%로 늘었다.
- p95가 양쪽 다 30초다. 30초는 k6의 요청 타임아웃 값이라,
  이 숫자는 "응답이 30초 걸렸다"가 아니라 "대부분 응답을 못 받았다"는 뜻이다.
- 부하는 4 rps에 불과했다. 초당 4건을 못 견뎠다.
- dropped_iterations가 50/51이다. 0이 아니므로 목표 부하를 다 만들지 못했다.

⚠ 풀 50 조건은 application.yml을 고치고 측정했으나 그 상태를 커밋하지 않았다.
  CLAUDE.md의 "설정만 바꾸는 경우에도 반드시 exp 커밋" 규칙을 못 지켰다.
  저장소의 f9362d9는 풀 10 상태다. 풀 50 수치는 커밋으로 재현되지 않는다.

================================================================
A-2. 오프셋 페이징 vs 커서 페이징
================================================================

updated_at 인덱스를 걸기 전후로 두 방식을 각각 쟀다.

              인덱스 없음   인덱스 있음
------------- ------------- -------------
오프셋        2.97 초       12.99 초
커서          0.29 초       0.014 초

관찰:
- 같은 인덱스 하나를 걸었는데 두 방식이 반대로 움직였다.
  커서는 0.29초 -> 0.014초로 좋아졌고, 오프셋은 2.97초 -> 12.99초로 나빠졌다.
- 인덱스가 있는 상태에서 오프셋과 커서의 차이는 12.99초 vs 0.014초다.
- 인덱스를 거는 것이 항상 이득은 아니라는 사례다.
  실행계획이 바뀌면서 손해가 나는 쿼리가 같은 테이블에 있을 수 있다.
