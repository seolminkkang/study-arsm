# 테크니컬 라이팅 가이드

기술 문서 작성의 전체 프로세스를 3단계로 안내한다.
이 스킬을 참조할 때는 사용자의 요청에 맞는 단계부터 적용하면 된다.

---

## Step 1. 문서 유형 정하기

문서를 쓰기 전에, 독자의 목적에 따라 유형을 먼저 결정한다.

| 유형 | 독자의 목적 | 예시 |
|------|------------|------|
| **학습 중심 문서** | 새로운 기술/도구를 처음 접해서 흐름을 알고 싶을 때 | 시작하기, 튜토리얼 |
| **문제 해결 문서** | 배경지식이 있는 상태에서 특정 문제를 해결하고 싶을 때 | How-to 가이드, 트러블슈팅 |
| **참조 문서** | 이미 기본 사용법을 아는 상태에서 API/함수 스펙을 확인하고 싶을 때 | API 레퍼런스, SDK 문서 |
| **설명 문서** | 개념, 원리, 배경 지식을 깊이 이해하고 싶을 때 | 아키텍처 설명, 도메인 문서 |

### 1-1. 학습 중심 문서

독자가 새로운 기술/도구를 배울 수 있도록 돕는 문서.

**핵심 원칙:**
- 처음부터 끝까지 막힘없이 진행할 수 있어야 한다. 모든 예제 코드는 실제 실행·검증 완료 상태여야 한다.
- 단계별로 설명한다. 간단한 것부터 점진적으로 난이도를 올린다.
- 실행 가능한 코드 예제를 포함한다. 각 단계 완료 시 기대 결과를 명시한다.

**시작하기 vs 튜토리얼:**
- 시작하기: 처음 접하는 독자가 주요 흐름/개념을 이해하도록 돕는 문서
- 튜토리얼: 명확한 목표와 결과물이 있는 단계별 실습 문서

**팁:**
- FAQ 섹션으로 자주 발생하는 문제와 해결책을 문서 마지막에 추가
- 접어둘 수 있는 컴포넌트로 부가 설명/심화 내용을 숨겨두기

**템플릿:**
```
# [튜토리얼 제목]
## 목표
[이 튜토리얼을 따라하고 나면 독자가 달성할 목표]
## 사전 요구사항
- [필요한 사전 지식, 설치할 도구]
## 단계별 가이드
### [첫 번째 단계 제목]
[작업 설명 + 코드 예제 + 실행 결과 확인 방법]
### [두 번째 단계 제목]
...
### 최종 결과 확인
[목표 달성 시 나오는 결과]
```

**체크리스트:**
- [ ] 학습 목표를 명확하게 제시했는가?
- [ ] 직접 따라 해 봤을 때 오류가 생기지 않는가?
- [ ] 단계별로 설명되어 있는가?
- [ ] 실행 가능한 코드 예제가 포함되어 있는가?

### 1-2. 문제 해결 문서

독자가 직면한 문제를 빠르고 효과적으로 해결할 수 있도록 돕는 문서.

**핵심 원칙:**
- 명확한 문제 상황을 정의한다. 원인과 현상을 구분하고, 에러 메시지/로그 예시를 포함한다.
- 바로 적용할 수 있는 해결 방법을 제공한다. 코드 예제, 명령어, 설정 방법을 포함한다.
- 환경별 차이를 고려한다. OS, 라이브러리 버전에 따른 차이를 설명한다.

**How-to 가이드 vs 트러블슈팅:**
- How-to 가이드: 특정 기능 구현에 초점. 단계별 실행 절차 + 실행 가능한 코드 예제.
- 트러블슈팅: 이미 발생한 문제를 진단하고 해결하는 데 중점. 에러 → 원인 → 해결 순서.

**템플릿 (문제 해결):**
```
# [문제 해결 문서 제목]
## 문제 정의
[독자가 겪을 수 있는 문제 상황]
## 사전 요구사항
[필요한 환경 설정이나 필수 조건]
## 해결 방법
### [첫 번째 해결 방법]
### [두 번째 해결 방법]
### 문제 해결 후 확인 방법
```

**체크리스트:**
- [ ] 에러에 대한 기본적인 지식도 충분히 제공했는가?
- [ ] 즉시 적용할 수 있는 해결 방법이 포함되어 있는가?
- [ ] 환경별 차이를 고려한 설명이 포함되어 있는가?

### 1-3. 참조 문서

독자가 특정 기술/도구/시스템에 대한 정확하고 완전한 정보를 빠르게 찾을 수 있도록 설계된 문서.

**핵심 원칙:**
- 정확성과 완전성이 중요하다. 기술적 오류나 모호한 설명 없이, 항상 최신 상태여야 한다.
- 일관된 구조로 작성한다. 함수 이름 → 매개변수 → 반환값 → 예제 코드 순서를 표준화한다.
- 검색과 탐색이 쉬워야 한다. 목차, 키워드 검색, 앵커 링크를 활용한다.
- 예제 코드를 제공한다.

**템플릿:**
```
# [참조 문서 제목]
## 개요
[이 요소가 무엇이며, 언제 사용하는지, 어떤 가치를 제공하는지]
## 시그니처
[함수/API의 시그니처]
## 매개변수
| 속성명 | 타입 | 기본값 | 설명 |
## 반환 값
[반환하는 값 설명]
## 사용 예제
[구체적인 예시 + 예제 코드]
```

**체크리스트:**
- [ ] 검색 및 탐색이 쉬운 구조인가?
- [ ] 정보가 정확하고 완전한가?
- [ ] 일관된 구조와 형식으로 작성되어 있는가?
- [ ] 실용적인 예시 코드가 포함되어 있는가?

### 1-4. 설명 문서 (깊은 이해)

독자가 특정 기술이나 개념을 깊이 있게 이해할 수 있도록 돕는 문서.

**핵심 원칙:**
- 배경 및 맥락을 제공한다. 기술이 등장한 이유와 해결하려는 문제를 먼저 설명한다.
- 시각 자료를 적극적으로 활용한다. 다이어그램, 흐름도, 표 등으로 복잡한 개념을 시각화한다.

**두 가지 하위 유형:**
- 개념 이해 문서: 특정 개념의 원리와 작동 방식 (예: React 가상 DOM 작동 원리)
- 도메인 문서: 특정 도메인에 대한 이해 (예: 커머스 도메인 이해하기)

**템플릿:**
```
# [개념명]
## 개념 소개
[이 개념이 무엇인지 간략히 설명]
## 등장 배경
[왜 등장했는지, 어떤 문제를 해결하는지]
## 활용
[실제 프로젝트에서 어떻게 사용되는지]
```

**체크리스트:**
- [ ] 핵심 원리와 배경이 명확하게 설명되었는가?
- [ ] 복잡한 개념을 시각화하여 설명했는가?
- [ ] 선행 지식이 충분히 안내되었는가?

## Step 2. 정보 구조 만들기

문서의 뼈대를 설계하는 단계. 독자 입장에서 설계하는 것이 핵심이다.

### 2-1. 한 페이지에서 하나만 다루기

한 문서에 너무 많은 내용을 담으면 독자가 핵심을 파악하기 어렵다.

**왜 중요한가:**
- 가독성이 높아지고 탐색이 쉬워진다
- 문서 유지보수가 쉬워진다
- 구조가 복잡해지는 것을 막는다

**실천 방법:**
- 제목 깊이가 H4(####) 이상이 되면 문서를 나누는 것을 고려한다.
- 여러 개념을 개략적으로 소개해야 한다면, 개별 문서로 연결되는 개요 페이지를 따로 만든다.
- 한 페이지에서 두 개 이상의 핵심 주제를 다루고 있다면 문서를 분리한다.

**Don't:** `# React 사용법 > ## 컴포넌트 생성 > ### 컴포넌트 기본 구조 > #### JSX 사용법 > ##### JSX 문법 세부사항`
**Do:** `# React 컴포넌트 생성하기 > ## 컴포넌트 기본 구조 > ## 상태 관리 > ## 라이프사이클 메서드`

### 2-2. 가치를 먼저 제공하기

기능 중심 설명보다는 독자가 얻을 수 있는 가치를 먼저 설명한다.

**왜 중요한가:**
- 기능 설명에만 집중하는 실수를 피할 수 있다. 독자는 "이 기능이 왜 필요한가?", "내게 어떤 도움이 되는가?"를 먼저 알고 싶어 한다.
- 독자의 관심을 빠르게 끌 수 있다.

**실천 방법:**
- 부가적인 정보나 세부 사항은 나중에 배치한다.
- 기능 중심 설명을 피하고, 독자가 얻을 가치를 먼저 전달한다.

**Don't:** "리버스 프록시 설정은 2019년에 도입되었고, 많은 수정이 있었습니다..."
**Do:** "리버스 프록시 설정을 적용하면 네트워크 지연 문제를 최소화할 수 있어요."

**Don't:** "이 스니펫은 다양한 설정 옵션을 제공합니다. 먼저 `connection_timeout`, `retry_attempts`..."
**Do:** "이 스니펫을 사용하면 PostgreSQL 데이터베이스 연결 속도가 50% 빨라집니다."

### 2-3. 효과적인 제목 쓰기

제목은 문서의 핵심 내용을 간결하고 명확하게 전달해야 한다.

**실천 방법:**
- 제목에는 핵심 키워드를 포함한다.
  - Don't: `# 에러를 해결하는 방법은?`
  - Do: `` # `NOT_FOUND_USER` 에러를 해결하는 방법 ``
- 일관성을 유지한다. 같은 수준의 소제목은 동일한 문체(예: ~하기)를 따른다.
- 제목은 30자 이내로 간결하게 쓴다.
- 제목은 평서문으로 작성한다. 느낌표(!)나 물음표(?) 대신 평서문을 사용한다.

### 2-4. 개요 빠트리지 않기

개요는 문서의 핵심 내용을 요약하고, 독자가 문서를 읽기 전에 내용을 빠르게 이해할 수 있도록 돕는다.

**실천 방법:**
- 개요는 문서의 핵심 내용을 요약해야 한다. 제목 바로 아래, 본문 시작 전에 배치한다.
- "이 문서를 읽으면 무엇을 할 수 있는가?"에 대한 답을 개요에서 제공한다.
- 기술적 배경 설명보다는 핵심 정보를 먼저 제공한다.

**Don't:**
```
# TypeScript의 유틸리티 타입
이 문서는 TypeScript의 유틸리티 타입을 소개합니다.
Partial, Pick, Omit 등의 유틸리티 타입을 사용할 수 있어요.
```

**Do:**
```
# TypeScript의 유틸리티 타입
TypeScript의 유틸리티 타입을 사용해서 객체 타입을 변형하는 방법을 알아볼게요.
유틸리티 타입을 활용하면 반복적인 타입 선언을 줄이고, 더 유연하게 타입을 관리할 수 있어요.
```

### 2-5. 예측 가능하게 하기

문서는 독자가 쉽게 탐색하고 필요한 정보를 빠르게 찾을 수 있도록 예측 가능해야 한다.

**실천 방법:**
- 일관된 제목, 형식, 구조를 유지한다.
- 섹션 제목은 동일한 패턴을 따른다. 설명 → 코드 순서를 지킨다.
- 논리적인 순서로 정보를 배치한다. 핵심 개념 → 구체적 사용법 → 예제 코드 → 심화 내용.
- 용어를 일관되게 사용한다. "상태", "데이터 저장", "값 유지"를 혼용하지 않는다.

### 2-6. 자세히 설명하기

독자는 문서를 처음 읽기 때문에 배경지식이 부족할 수 있다.

**실천 방법:**
- 새로운 개념이 등장하면 자세히 설명한다.
  - Don't: "이 서비스는 이벤트 소싱 방식을 사용해 상태를 관리합니다."
  - Do: "이 서비스는 이벤트 소싱(Event Sourcing) 방식을 사용해 상태를 관리합니다. 이벤트 소싱은 상태의 최종 결과만 저장하는 대신, 상태 변화를 일으킨 모든 이벤트를 기록하는 방식입니다."
- 기능이 어떤 조건에서 어떻게 동작하는지 정보를 충분히 제공한다. 단위, 동작 조건, 예외 상황을 명시한다.

## Step 3. 문장 다듬기

개별 문장의 품질을 높이는 단계.

### 3-1. 문장의 주체를 분명하게 하기

기술 문서에서는 문서를 읽는 사람(개발자)이 곧 행동의 주체다.

**실천 방법:**
- 도구나 기술, 시스템을 행동의 주체로 사용하지 않는다.
  - Don't: "**이 라이브러리는** 데이터베이스 초기화를 수행해요."
  - Do: "이 명령어를 실행하면 데이터베이스를 초기화할 수 있어요."
- 능동형으로 표현한다.
  - Don't: "애플리케이션이 실행되기 전에 설정이 완료되어야 합니다."
  - Do: "애플리케이션을 실행하기 전에 설정을 완료하세요."

(단, 도구/기술의 동작 자체를 설명할 때는 주체가 도구/기술이 될 수 있다.)

### 3-2. 필요한 정보만 남기기

한 문장에 하나의 생각만 담는다.

**실천 방법:**
- 문장을 짧고 간결하게 유지한다.
  - Don't: "버튼을 클릭하면 다음 단계로 이동하게 되며, 그 이후의 작업을 진행할 수 있습니다."
  - Do: "버튼을 클릭하면 다음 단계로 이동합니다. 이동 후 이어서 작업을 진행하세요."
- 메타 담화를 최소화한다. '앞에서 설명했지만', '아시다시피', '결론적으로' 같은 표현을 제거한다.
  - Don't: "아시다시피, 이 설정은 성능에 영향을 줍니다."
  - Do: "이 설정은 성능에 영향을 줍니다."

### 3-3. 구체적으로 쓰기

모호하거나 장황한 표현은 독자의 이해를 방해한다.

**실천 방법:**
- 명사 대신 동사를 사용한다.
  - Don't: "코드 최적화 진행 후 배포 수행이 필요합니다."
  - Do: "코드를 최적화한 후 배포하세요."
- 모호한 표현 대신 명확한 표현을 사용한다.
  - Don't: "일부 브라우저에서 정상적으로 동작하지 않을 가능성이 있습니다."
  - Do: "Internet Explorer에서는 정상적으로 동작하지 않습니다."
- 누가, 무엇을, 어디에, 어떻게 하는지 써준다.
  - Don't: "파일을 업로드하면 자동으로 저장됩니다."
  - Do: "사용자가 파일을 업로드하면 서버에 자동으로 저장됩니다."
- 구체적인 수치나 기준을 제시한다.
  - Don't: "데이터가 많을 때는 성능이 저하될 수 있습니다."
  - Do: "데이터가 10,000건을 넘으면 응답 시간이 1초 이상 걸립니다."
- 참조되는 내용의 맥락을 설명한다. 어디에서 설명했는지, 나중에 어디서 쓰이는지 링크와 함께 안내한다.

### 3-4. 자연스러운 한국어 표현 쓰기

**실천 방법:**
- 불필요한 한자어를 제거한다.
  - Don't: "로그 파일을 삭제하는 작업을 수행합니다."
  - Do: "로그 파일을 삭제합니다."
- 번역체 표현을 자연스럽게 수정한다. 영어식 명사형 표현을 동사 중심으로 바꾼다.
  - Don't: "API 키를 이용한 사용자 인증 처리가 완료된 후, 데이터베이스 접속 설정 진행이 가능합니다."
  - Do: "API 키로 사용자를 인증한 후, 데이터베이스에 접속하도록 설정할 수 있습니다."

### 3-5. 일관되게 쓰기

**실천 방법:**
- 공식 기술 용어를 따른다. 위키피디아 및 공식 문서의 표기를 기준으로 한다. 대소문자에 유의한다.
- 같은 개념을 여러 방식으로 표현하지 않는다. "추가", "첨부", "넣다"를 혼용하지 않고 하나로 통일한다.
- 약어는 먼저 풀어쓴 후 사용한다. 예: "SSR(Server-Side Rendering)"
- 외래어 표기는 사용 빈도를 고려한다. 업계에서 일반적으로 쓰이는 표현을 우선한다. 예: "프런트엔드" → "프론트엔드"

## 활용 가이드

이 스킬을 사용할 때의 워크플로우:

1. **문서 유형을 먼저 결정한다** (Step 1). 독자가 학습/문제해결/참조/깊은이해 중 어떤 목적인지 파악한다.
2. **정보 구조를 설계한다** (Step 2). 한 페이지 하나의 주제, 가치 우선, 효과적인 제목, 개요, 예측 가능한 구조, 충분한 설명.
3. **문장을 다듬는다** (Step 3). 주체 분명, 간결, 구체적, 자연스러운 한국어, 일관된 용어.

문서 리뷰 시에는 Step 2 → Step 3 순서로 구조 → 문장 레벨을 점검한다.
