02 · 핵심 요약

4장은 기다리는 동안 우리 서비스를 보호하고, 5장은 기다림과 복구 책임을 다른 시간과 장소로 옮깁니다.

왜 4장과 5장을 같이 보나?

4장은 무엇을 해결하나?

  • 두 장은 서로 다른 기술 목록이 아니라 하나의 설계 질문을 앞뒤에서 다룹니다.
  • 주문 서비스 A가 포인트 서비스 B에 일을 부탁한다고 해봅시다.
  • A가 B의 답을 기다리면 구현과 사용자 경험은 단순하지만, B의 지연과 장애가 A의 응답 경로로 곧장 들어옵니다.
  • 4장은 이 동기 경로를 유지하면서 피해가 커지지 않도록 타임아웃, 재시도, 동시성 제한, 서킷 브레이커 같은 경계를 세웁니다.

5장으로 가면 무엇이 달라지나?

  • 반대로 포인트 지급 결과가 지금 응답에 꼭 필요하지 않다면 A는 일을 나중으로 미룰 수 있습니다.
  • 5장은 별도 스레드, 메시지 브로커, 배치, CDC 같은 방식으로 처리 시점을 분리합니다.
  • 그러나 분리한 순간 “호출에 성공했는가?”라는 단순한 질문이 “작업은 안전하게 보관됐는가, 누가 실패를 재처리하는가, 같은 작업이 두 번 오면 어떻게 하는가?”라는 새 질문으로 바뀝니다.
동기 경로의 핵심사용자의 응답과 B의 결과가 같은 시간선에 있습니다. 이해하기 쉽지만 장애도 같은 경로로 전파됩니다.
비동기 경로의 핵심사용자 응답과 실제 작업 완료가 다른 시간선에 있습니다. 결합은 줄지만 상태가 더 많아집니다.
공통 설계 원칙실패를 없애는 대신 실패가 머물 장소, 기다릴 시간, 다시 처리할 책임을 명시합니다.

이 페이지 전체에서 같은 `주문 생성 → 포인트 지급` 사례를 반복합니다. 기술이 바뀔 때 요청과 데이터의 위치가 어떻게 달라지는지를 중심으로 보세요.

04 · 예시로 연결하기

주문은 저장됐는데 포인트 서비스가 느립니다. 포인트 지급까지 기다리면 주문 응답도 늦어집니다.

적립이 조금 늦어도 되는 정책이라면 주문 접수를 먼저 알리고 적립은 나중에 처리할 수 있습니다.

단, “접수됐다”와 “적립이 끝났다”는 같은 성공이 아닙니다.

01 · 단어 정의

처리량

02 · 핵심 요약

B의 지연은 A의 자원 점유 시간을 늘립니다. CPU가 한가해도 풀과 대기열은 가득 찰 수 있습니다.

한 요청이 느린 것과 서비스가 무너지는 것은 어떻게 연결될까?

왜 상대가 느린데 우리가 멈추나?

  • A가 B를 동기 호출하면 A의 요청 처리 스레드는 B의 응답이 올 때까지 그 요청을 끝낼 수 없습니다.
  • 기다리는 동안 CPU를 계속 쓰는 것은 아니지만, 스레드와 HTTP 커넥션 같은 유한한 자원은 그 요청에 묶여 있습니다.
  • B가 평소 100ms 만에 답하면 연결 하나는 1초에 여러 요청을 처리할 수 있지만, 응답 시간이 5초가 되면 같은 연결은 훨씬 오래 점유됩니다.
  1. B의 응답 시간이 길어진다.
    새 요청 수가 그대로여도 각 요청이 시스템 안에 머무는 시간이 늘어납니다.
  2. A에서 동시에 진행 중인 요청이 늘어난다.
    요청 스레드와 B용 HTTP 커넥션이 더 오래 사용 중 상태로 남습니다.
  3. 풀이 가득 차고 대기열이 생긴다.
    새 요청은 실제 업무를 시작하지도 못한 채 스레드나 커넥션을 기다립니다.
  4. A 자체의 응답도 느려진다.
    B를 사용하지 않는 기능까지 같은 스레드 풀을 공유한다면 피해가 다른 기능으로 번질 수 있습니다.
  5. 사용자나 상위 서비스가 재시도한다.
    유입량이 더 커져 회복할 틈을 빼앗는 연쇄 장애(cascading failure)가 됩니다.
CPU가 낮아도 안전한 것은 아니다서버가 놀고 있는 것처럼 보여도 요청 스레드, HTTP 커넥션, DB 커넥션 또는 큐가 꽉 찼다면 이미 포화(saturation) 상태일 수 있습니다.

평균 응답 시간만 보면 놓치는 것

  • 대부분의 요청이 빠르고 일부만 매우 느리면 평균값은 멀쩡해 보입니다.
  • 사용자 다수가 체감하는 느린 구간을 보려면 p95와 p99 같은 꼬리 지연(tail latency)도 함께 관찰해야 합니다.
  • 예를 들어 p99가 4초라면 요청 100개 중 약 1개가 4초 이상 걸렸다는 뜻으로 해석할 수 있습니다.

아래 모형에서는 B의 응답 시간을 올려보세요. 유입 요청이 그대로인데도 필요한 동시 진행 수가 늘고, 어느 순간 완료 속도보다 유입 속도가 커지는 경계를 확인할 수 있습니다.

04 · 예시로 연결하기

비유: 창구 직원 4명이 각각 본사 승인 전화를 기다리고 있습니다. 직원이 바쁘게 움직이지 않아도 새 손님을 받을 창구는 없습니다.

전화 대기가 길어질수록 줄이 길어집니다. 서버에서도 응답 대기가 길어지면 스레드·연결이 오래 묶입니다.

비유의 범위: 블로킹 호출의 자원 점유를 설명합니다. 모든 서버가 요청 하나당 OS 스레드 하나를 쓰는 것은 아닙니다.

05 · 실습 — 수치로 확인하기먼저 유입 요청은 그대로 두고 B 응답 시간만 천천히 늘리세요.

필요한 동시 진행 요청이 슬롯을 넘어가는 순간부터 대기가 누적됩니다.

볼 것: 필요 동시 요청 → 초당 밀리는 요청 → p95의 순서로 무엇이 먼저 악화되는가

166/s이론적 B 호출 처리 한계
24필요한 동시 진행 요청

모형의 한계이 계산은 개념 학습용 근사치입니다. 실제 처리량은 CPU, 네트워크, 큐 정책, 요청별 처리 시간 분포와 HTTP 버전에 따라 달라집니다.

02 · 핵심 요약

기다림을 제한하는 것과 상대 작업을 취소하는 것은 다릅니다. 단계별 제한과 전체 예산을 함께 봅니다.

타임아웃은 실패를 만드는 설정이 아니라 기다림의 상한선이다

왜 제한이 필요한가?

  • 타임아웃을 설정하면 정상 요청도 실패할 수 있으므로 처음에는 불편하게 느껴집니다.
  • 하지만 타임아웃이 없으면 장애 난 요청 하나가 언제 끝날지 모르는 채 자원을 점유합니다.
  • 타임아웃의 목적은 성공률을 무조건 높이는 것이 아니라, 한 의존성 때문에 우리 서비스가 사용할 수 있는 시간과 자원이 무한정 소비되지 않도록 경계를 세우는 데 있습니다.

하나의 HTTP 호출에서 무엇을 기다리나?

  • 중요한 점은 HTTP 호출이 한 번의 기다림으로 이루어지지 않는다는 것입니다.
  • 이미 만들어 둔 연결이 모두 사용 중이면 먼저 풀에서 커넥션을 기다립니다.
  • 새 연결이 필요하면 DNS 조회, TCP 연결, HTTPS의 TLS 협상이 이어집니다.
  • 그 뒤 요청을 보내고 서버가 처리하여 응답 데이터를 돌려줄 때까지 다시 기다립니다.
  • 라이브러리마다 이름과 포함 범위가 조금씩 다르기 때문에 “5초 타임아웃을 걸었다”만으로는 어느 구간을 제한했는지 알 수 없습니다.
풀 대기우리 프로세스 안에서 사용 가능한 연결을 빌리지 못해 기다리는 시간입니다. B에 패킷을 보내기도 전입니다. 연결 수립원격 주소로 네트워크 연결을 만드는 시간입니다. 네트워크 단절, 잘못된 라우팅, 방화벽 등의 영향을 받습니다. 응답 대기연결 뒤 B의 처리 또는 데이터 수신을 기다리는 시간입니다. B의 과부하와 느린 쿼리가 드러나는 구간입니다. 전체 예산위 단계와 재시도를 모두 합쳐 이 업무가 기다릴 수 있는 총 시간입니다. 상위 요청의 deadline보다 길면 의미가 없습니다.
가장 위험한 오해클라이언트가 타임아웃 예외를 받았다는 사실은 B의 처리가 취소됐다는 뜻이 아닙니다. B가 처리를 끝낸 직후 응답만 유실됐을 수도 있습니다. 결제·포인트처럼 부작용이 있는 요청은 이 결과 불명확 상태를 반드시 설계해야 합니다.

아래 슬라이더는 네 구간의 합과 전체 deadline을 비교합니다. 실제 설정에서는 각 구간별 제한과 업무 전체 예산을 함께 보아야 합니다.

타임아웃 ≠ 원격 작업 취소A가 실패를 관찰했어도 B는 이미 포인트를 지급했을 수 있습니다. 이것이 결과 불명확(ambiguous outcome)입니다.

핵심 외부 서비스의 이중화는 ‘주소를 두 개 적는 일’이 아니다

결제·본인인증처럼 이 기능이 멈추면 핵심 업무 자체가 멈추는 의존성은 대체 경로를 검토할 수 있습니다. 하지만 결제사 A가 실패하면 결제사 B를 호출한다는 코드만으로 복원력이 생기지는 않습니다. 두 제공자의 요청·응답 모델, 오류 코드, 인증 방식, 정산과 취소 절차가 다르며, 전환 도중 첫 번째 요청이 실제 성공했는지 모르는 결과 불명확 문제도 남습니다.

전환 조건연결 실패, 타임아웃, 특정 5xx 중 무엇을 장애로 볼지 정합니다. 잘못된 입력 같은 4xx를 다른 업체로 반복해서 보내면 대체 경로도 실패합니다.
중복 효과 방지첫 제공자가 처리했지만 응답이 유실된 뒤 두 번째 제공자로 전환하면 이중 결제·이중 발송이 생길 수 있습니다. 업무 키와 상태 조회·보상 절차가 필요합니다.
운영 현실용량, 계약, 비용, 데이터 형식, 개인정보 이전, 정산 대사와 장애 훈련까지 유지해야 실제 대체 경로가 됩니다.

이중화는 모든 외부 연동에 붙이는 기본 옵션이 아닙니다. 장애 손실이 이중화의 개발·운영·계약 비용보다 큰 핵심 기능인지부터 판단하고, 평상시에도 대체 경로를 시험해야 합니다.

02 · 핵심 요약

Keep-Alive는 연결을 살려두는 것, 풀은 그 연결을 관리하며 빌려주는 것입니다. 응답 데이터를 캐시하는 것은 아닙니다.

연결을 만드는 비용과, 연결을 빌리는 규칙을 나누어 생각하자

연결을 왜 재사용하나?

  • HTTPS 요청을 보낼 때마다 새 연결을 만든다면 TCP 연결과 TLS 협상을 반복해야 합니다.
  • 같은 목적지에 요청을 자주 보낸다면 이미 만든 연결을 다음 요청에도 사용하는 편이 빠릅니다.
  • HTTP의 지속 연결, 흔히 말하는 Keep-Alive는 요청 하나가 끝난 뒤에도 연결을 즉시 닫지 않아 재사용할 수 있게 하는 성질입니다.

풀은 구체적으로 무슨 일을 하나?

  • 하지만 살아 있는 연결이 있다는 사실만으로 여러 스레드가 안전하고 효율적으로 공유할 수 있는 것은 아닙니다.
  • 커넥션 풀은 연결들을 보관하고, 요청에게 빌려주고, 사용이 끝나면 돌려받고, 너무 오래 놀았거나 수명이 끝난 연결을 폐기하는 관리 장치입니다.
  • DB 커넥션 풀과 빌리고 반납한다는 모양은 비슷하지만, HTTP 연결은 프로토콜 버전과 목적지별 route, 상대 서버의 keep-alive 정책까지 영향을 받습니다.
  1. 요청이 들어오면 클라이언트는 해당 목적지에 재사용 가능한 연결이 있는지 찾습니다.
  2. 유휴 연결이 있으면 빌립니다. 없지만 풀 한도가 남았다면 새 연결을 만듭니다.
  3. 한도까지 모두 사용 중이면 요청은 풀 앞 대기열에 들어가거나 즉시 거절됩니다.
  4. 응답 처리가 끝나고 재사용 가능한 연결이면 풀에 반환합니다. 연결이 깨졌거나 수명이 끝났다면 닫습니다.

왜 풀을 무조건 크게 하면 안 될까?

  • 풀이 작으면 요청이 풀 앞에서 기다려 전체 응답 시간이 늘 수 있습니다.
  • 그러나 풀이 너무 크면 A가 B의 처리 한계를 훨씬 넘는 요청을 한꺼번에 보낼 수 있습니다.
  • 그러면 B가 더 느려지고 A의 연결이 더 오래 점유되어 양쪽이 함께 악화됩니다.
  • 풀 크기는 단순 성능 수치가 아니라 A가 B에 허용하는 동시 부하의 상한이라는 관점으로 보아야 합니다.
RestClient라는 이름만으로 기본 풀 크기를 알 수 없다Spring `RestClient`는 상위 API입니다. 실제 연결 재사용과 제한은 Apache HttpClient, JDK HttpClient, Jetty, Reactor Netty 또는 단순 request factory 중 어떤 구현을 쓰는지에 따라 달라집니다. 클라이언트 인스턴스도 요청마다 만들지 말고 애플리케이션에서 재사용 가능한 형태로 구성해야 합니다.

04 · 예시로 연결하기

비유: 같은 거래처와 통화할 전화선이 4개 있습니다. 통화가 끝나면 선을 없애지 않고 다음 담당자에게 빌려줍니다.

HTTP/1.1의 단순 모형에서 요청 7개가 동시에 오면 4개가 연결을 사용하고 3개는 반환을 기다립니다.

비유의 범위: HTTP/2는 한 연결에서 여러 스트림을 동시에 처리할 수 있습니다. 따라서 전화선 수와 동시 요청 수가 항상 같지는 않습니다.

05 · 실습 — 풀에서 빌리고 기다리는 과정 보기풀 크기 4, 동시 요청 7인 기본 상태부터 읽으세요.

HTTP/2에서는 왜 풀 크기와 동시 요청 수가 같지 않을까?

HTTP/1.1의 전형적 연결 사용과 달리 HTTP/2는 한 연결 안에서 여러 스트림을 다중화할 수 있습니다. 그래서 연결 1개가 동시에 요청 여러 개를 운반할 수 있습니다. 단, 실제 최대 스트림 수와 풀 정책은 클라이언트·서버 설정에 달려 있습니다.

재시도하고, 제한하고, 빠르게 실패하기

장치마다 보호하는 경계가 다릅니다. 여러 장치를 켠다고 자동으로 안전해지는 것도 아닙니다.

01 · 단어 정의

재시도
실패한 작업을 정해진 조건에서 다시 실행하는 것
멱등성
같은 연산을 반복해도 한 번 실행한 것과 같은 효과가 남는 성질
서킷 브레이커
실패가 누적된 의존성으로의 호출을 잠시 차단하고 회복을 시험하는 장치

02 · 핵심 요약

재시도는 다시 보내는 판단이고, 서킷은 보내지 않는 판단입니다. 중복 효과와 추가 부하를 먼저 따져야 합니다.

복원력 패턴은 모두 “호출을 더 성공시키는 기능”이 아니다

언제 다시 보내도 되나?

  • 일시적인 패킷 유실이나 짧은 서버 재시작처럼 곧 회복되는 실패라면 재시도가 성공 확률을 높입니다.
  • 하지만 B가 이미 과부하이거나 잘못된 입력 때문에 거절한 요청이라면 재시도는 같은 실패를 반복하며 부하만 늘립니다.
  • 그래서 재시도 여부는 오류 코드 하나가 아니라 실패의 일시성, 업무 연산의 멱등성, 남은 시간 예산, 현재 의존성의 상태를 함께 보고 결정해야 합니다.

멱등하다는 것은 무엇인가?

  • 멱등성(idempotency)은 같은 연산을 여러 번 적용해도 최종 결과가 한 번 적용했을 때와 같다는 성질입니다.
  • 단순 조회는 보통 멱등하지만, “100포인트 추가”는 그대로 두 번 실행하면 200포인트가 되어 멱등하지 않습니다.
  • 이때 요청마다 고유한 idempotency key를 보내고 B가 이미 처리한 키를 기억하면 동일 요청의 재실행을 한 번의 효과로 제한할 수 있습니다.
재시도이번 실패가 일시적이라고 보고 다시 기회를 줍니다. 횟수와 간격, 대상 오류를 제한합니다.
동시성 제한·벌크헤드실행 중인 작업 수와 사용 자원을 제한하여 한 의존성의 지연이 다른 기능까지 번지는 것을 막습니다.
서킷 브레이커최근 관찰 결과상 성공 가능성이 낮으면 실제 호출을 잠시 중단하여 자원 낭비와 추가 부하를 줄입니다.

백오프와 지터가 필요한 이유

  • 장애가 나면 여러 인스턴스와 사용자가 비슷한 시점에 실패를 관찰합니다.
  • 모두 1초 뒤에 다시 시도하면 정확히 1초마다 요청이 한꺼번에 몰립니다.
  • 지수 백오프는 실패할수록 간격을 늘리고, 지터는 각 호출의 간격을 조금씩 흩어 회복 중인 B에 재시도가 동기화되는 현상을 줄입니다.
패턴을 조합하면 순서도 설계다재시도가 서킷 브레이커의 실패 통계 안쪽에 있는지 바깥쪽에 있는지, 동시성 슬롯을 한 번의 업무가 잡는지 각 재시도가 새로 잡는지에 따라 관찰 결과가 달라집니다. 라이브러리 애너테이션을 여러 개 붙이는 것만으로 의도한 보호가 완성되지 않습니다.

아래에서 재시도 간격을 먼저 비교하고, 이어서 서킷의 상태를 바꿉니다. 각 장치가 요청을 성공시키는지보다 “어떤 요청을 아예 보내지 않는가”를 관찰하세요.

재시도는 실패한 한 요청에 다시 기회를 주고, 서킷 브레이커는 최근 실패가 계속될 때 새 요청을 B로 보내지 않습니다.

구분동시성 제한은 “한 시점에 몇 개”, rate limit은 대체로 “일정 시간에 몇 개”를 묻습니다. 과부하 제한에는 429와 Retry-After가, 현재 의존성 장애에는 503이 더 적절할 수 있지만 최종 상태 코드는 API 계약에 따라 결정합니다.
06 · Ambiguous outcome

DB는 롤백됐는데 포인트는 지급됐다면?

01 · 단어 정의

로컬 트랜잭션
한 DB 등 해당 트랜잭션에 참여한 자원의 변경을 함께 커밋·롤백하는 범위
보상
이미 완료된 일을 취소·환불 같은 별도 작업으로 되돌리는 것
대사

02 · 핵심 요약

우리 DB 롤백은 외부 서비스의 성공까지 취소하지 않습니다. 각 시스템에 실제로 무엇이 남았는지 따로 봐야 합니다.

트랜잭션 안에 HTTP 호출을 적어도 원격 시스템은 트랜잭션 밖에 있다

트랜잭션 경계는 어디까지인가?

  • Spring 메서드에 `@Transactional`이 붙어 있고 그 안에서 포인트 API를 호출한다고 해봅시다.
  • 주문 DB의 변경은 커밋하거나 롤백할 수 있지만, HTTP 너머에 있는 포인트 서비스는 주문 DB의 로컬 트랜잭션에 참여하지 않습니다.
  • 포인트 지급이 끝난 뒤 주문 DB 커밋이 실패해도 주문 서비스가 포인트 서비스의 데이터까지 자동으로 되돌릴 수는 없습니다.

응답을 못 받으면 무엇을 모르는가?

  • 더 까다로운 경우는 A가 결과를 모르는 때입니다.
  • B가 포인트를 반영한 뒤 응답을 보내는 순간 네트워크가 끊기면 A에는 읽기 타임아웃이 발생합니다.
  • A가 보는 사실은 “응답을 받지 못했다”뿐이며, “B가 처리하지 않았다”가 아닙니다.
  • 이 상태에서 곧바로 같은 지급 요청을 다시 보내면 중복 반영될 수 있습니다.
보상 작업이미 완료된 원격 부작용을 취소·환불처럼 업무적으로 되돌리는 별도의 연산입니다. 원래 트랜잭션의 롤백과는 다릅니다.
대사(reconciliation)두 시스템의 기록을 주기적으로 비교해 누락과 불일치를 찾아 자동 또는 수동으로 바로잡습니다.
Saga여러 로컬 트랜잭션과 보상 동작을 하나의 긴 업무 흐름으로 관리하는 접근입니다.

DB 트랜잭션 안에서 외부 호출을 오래 기다릴 때의 부작용

  • 네트워크를 기다리는 동안 주문 DB 커넥션과 행 락이 유지될 수 있습니다.
  • 외부 서비스가 느려지면 HTTP 풀뿐 아니라 DB 풀까지 함께 고갈되어 전혀 다른 DB 기능도 멈출 수 있습니다.
  • 따라서 데이터 정합성만 보고 트랜잭션 범위를 길게 잡지 말고, 자원 점유와 실패 복구 절차까지 함께 판단해야 합니다.

아래 실패 지점 네 가지를 바꿔보세요. “어디서 예외가 났는가”보다 각 시스템에 실제로 어떤 효과가 남았는지를 추적해야 합니다.

로컬 트랜잭션의 경계

주문 DB의 트랜잭션은 원격 포인트 서비스의 DB를 자동으로 롤백하지 않습니다. HTTP 호출을 트랜잭션 안에서 오래 기다리면 주문 DB 커넥션과 락도 오래 점유할 수 있습니다.

읽기 타임아웃의 함정A가 응답을 못 받았다는 사실만으로 B가 실패했다고 결론낼 수 없습니다.

복구 계약에 들어갈 것

  • idempotency key
  • 상태 조회 또는 결과 확인
  • 취소·환불 같은 보상 작업
  • 주기적인 데이터 대사(reconciliation)
  • 실패 상태와 수동 처리 절차

07 · Async boundary

빨리 응답한 것과 작업을 지킨 것은 다르다

01 · 단어 정의

비동기
현재 흐름이 작업 완료를 기다리지 않고 진행할 수 있는 방식
Executor
제출받은 작업을 스레드와 큐를 이용해 실행하는 구성 요소
블로킹

02 · 핵심 요약

빨리 응답해도 실제 업무는 남습니다. 누가 기다리고, 작업이 어디에 저장되며, 실패를 누가 처리하는지 확인합니다.

비동기는 “동시에 실행한다”보다 “완료를 나중에 다룬다”에 가깝다

무엇이 먼저 끝나고 무엇이 남나?

  • 동기 호출에서는 포인트 지급 결과가 돌아와야 로그인이나 주문 요청의 다음 줄을 실행합니다.
  • 비동기 호출에서는 작업을 다른 실행 주체에게 넘기고 현재 흐름은 먼저 진행합니다.
  • 따라서 사용자에게 빠르게 응답할 수 있지만, 응답 이후에도 포인트 지급이라는 실제 업무는 계속 남아 있습니다.

비동기와 논블로킹은 같은 말인가?

  • 여기서 자주 섞이는 용어가 동기·비동기와 블로킹·논블로킹입니다.
  • 동기·비동기는 완료 결과를 같은 제어 흐름에서 확인하는지에 관한 말이고, 블로킹·논블로킹은 기다리는 동안 현재 실행 스레드가 멈추는지에 관한 말입니다.
  • 별도 스레드에서 기존 `RestClient` 호출을 실행하면 원래 요청 스레드는 빨리 풀리지만, 별도 스레드는 여전히 네트워크 응답을 기다리는 블로킹 호출을 수행합니다.
  1. 요청 스레드가 비동기 작업을 executor에 제출합니다.
  2. 큐에 자리가 있으면 작업이 대기하고, 작업 스레드가 비면 실행됩니다.
  3. 요청 스레드는 실제 작업 완료보다 먼저 사용자에게 응답할 수 있습니다.
  4. 비동기 작업의 실패는 이미 끝난 사용자 요청으로 되돌아갈 수 없으므로 별도의 재시도·로그·상태 저장이 필요합니다.
풀 크기동시에 실행할 작업 수를 제한합니다. 너무 크면 외부 서비스와 JVM에 과부하를 줄 수 있습니다.
큐 크기당장 실행하지 못한 작업을 메모리에 보관합니다. 무제한 큐는 지연과 메모리 사용을 숨깁니다.
거절 정책풀과 큐가 모두 찼을 때 호출자 실행, 즉시 실패, 폐기 등 어떤 결정을 할지 정합니다.
메모리 큐는 업무 기록이 아니다프로세스가 재시작되면 executor 큐에 있던 작업은 사라질 수 있습니다. 반드시 처리해야 하는 업무라면 DB나 내구성 있는 브로커에 작업 의도를 먼저 기록해야 합니다.

`@Async`가 붙었다고 항상 비동기로 실행되지는 않는다

  • Spring의 기본 방식은 프록시가 메서드 호출을 가로채 executor에 제출하는 구조입니다.
  • 같은 객체 안에서 자기 메서드를 직접 호출하면 프록시를 지나지 않아 기대한 비동기 실행이 적용되지 않을 수 있습니다.
  • 또한 `void` 비동기 메서드의 예외는 원래 호출자의 `try-catch`에 도달하지 않으므로 별도 예외 처리와 실패 기록이 필요합니다.

01 · 단어 정의

브로커

Backlog
아직 처리하지 못해 남아 있는 메시지
ACK
메시지를 받거나 처리했다는 확인 신호. 정확한 의미는 시스템·설정에 따라 다릅니다.

02 · 핵심 요약

큐는 속도 차이를 흡수할 뿐 일을 없애지 않습니다. 밀린 양과 중복 전달에 대비해야 합니다.

메시지 브로커는 A와 B 사이에 시간을 저장한다

중간에 브로커를 두면 무엇이 바뀌나?

  • 동기 HTTP에서는 A가 B의 처리 가능 여부를 즉시 마주합니다.
  • 메시징에서는 A가 처리할 내용을 메시지로 만들어 브로커에 맡기고, B의 소비자가 자기 속도에 맞춰 가져갑니다.
  • B가 잠시 느려져도 브로커에 여유가 있다면 A는 B의 순간 처리 속도와 분리됩니다.
  • 이것을 느슨한 결합이라고 부르지만, B의 일이 사라진 것은 아니며 처리되지 않은 양은 backlog로 쌓입니다.

빠른 접수 응답 뒤에 무엇이 쌓이나?

  • 생산 속도가 초당 100건이고 소비 속도가 초당 80건이면 매초 20건씩 밀립니다.
  • 사용자는 주문 접수 응답을 빨리 받아도 포인트 지급 완료는 점점 늦어집니다.
  • 따라서 비동기 시스템에서는 API 응답 시간뿐 아니라 큐 깊이, 가장 오래된 메시지의 나이, 소비 지연, 실패·재시도율을 관찰해야 합니다.

왜 같은 메시지가 다시 올까?

  • 소비자가 포인트를 정상 반영한 뒤 브로커에 완료 확인을 보내기 전에 죽었다고 합시다.
  • 브로커는 처리가 끝났다는 사실을 알지 못하므로 같은 메시지를 다시 전달할 수 있습니다.
  • 반대로 완료 확인을 너무 일찍 보내고 실제 처리 전에 죽으면 메시지는 완료된 것으로 보이지만 업무는 반영되지 않습니다.
  • 분산 시스템에서 처리 결과와 확인 신호 사이에는 항상 이런 작은 간극이 생길 수 있습니다.
At-most-once중복 처리를 피하는 대신 실패 구간에서 메시지를 잃을 수 있습니다.
At-least-once유실 가능성을 줄이는 대신 같은 메시지가 둘 이상 도착할 수 있습니다.
Effectively-once중복이 올 수 있음을 인정하고 멱등 처리와 기록으로 업무 효과를 한 번처럼 만듭니다.

멱등 소비자의 기본 모양

  • 메시지에 고유 ID를 부여하고, 소비자는 업무 반영과 “이 ID를 처리했다”는 기록을 가능한 한 같은 DB 트랜잭션에서 저장합니다.
  • 재수신 시 처리 기록이 있으면 업무를 다시 적용하지 않습니다.
  • 메모리 집합만 사용하면 재시작 때 기록이 사라지고 여러 소비자 인스턴스 사이에서 공유되지 않으므로, 신뢰성이 필요한 경우 DB의 고유 제약 같은 영속적 장치를 사용합니다.

순서 보장도 범위가 있다

  • Kafka처럼 파티션을 사용하는 시스템에서는 보통 같은 파티션 안의 순서를 다룹니다.
  • 주문 ID를 키로 사용하면 같은 주문의 이벤트가 같은 파티션으로 가도록 설계할 수 있지만, 서로 다른 주문 사이의 전역 순서까지 보장되는 것은 아닙니다.
  • 소비자 병렬성을 높일수록 순서 보장 범위와 처리량 사이의 선택이 생깁니다.
제품 이름보다 필요한 보장을 먼저 정한다메시지를 다시 읽어야 하는지, 한 소비자만 처리할지 여러 구독자가 볼지, 순서 범위가 어디인지, 얼마나 오래 보관할지부터 정한 뒤 Kafka·RabbitMQ·Redis Pub/Sub 같은 제품을 비교해야 합니다.

첫 실험에서는 생산과 소비 속도를 바꾸고, 다음 실험에서는 같은 메시지를 두 번 전달해보세요. 멱등 소비자를 켰을 때 처리 횟수와 업무 결과가 어떻게 분리되는지 확인합니다.

커맨드: 누군가에게 일을 요청한다

“주문 42의 포인트 100점을 지급하라”처럼 수행할 작업, 대상, 의도가 들어갑니다. 보통 책임질 논리적 수신자가 있으며 성공·거절·재시도 같은 처리 결과가 중요합니다.

  • 명령형 이름: GrantPoints, SendDeliveryNotice
  • 업무상 한 번만 실행돼야 한다면 command ID와 멱등 키가 필요
  • 유효 기간이 지난 커맨드를 실행해도 되는지 만료 정책을 정의
  • 처리 불가능한 메시지는 재시도만 반복하지 말고 별도 격리

커맨드를 여러 소비자가 각자 다른 의미로 처리하게 만들면 책임 소재가 흐려집니다.

이벤트: 이미 일어난 사실을 알린다

“주문 42가 접수됐다”처럼 과거형 사실을 담습니다. 발행자는 누가 반응할지 몰라도 되며, 포인트·알림·분석 소비자가 독립적으로 구독할 수 있습니다.

  • 사실형 이름: OrderPlaced, DeliveryCompleted
  • 이미 일어난 사실이므로 소비자가 없다고 발행 사실이 취소되지는 않음
  • 새 소비자를 추가해도 생산자 코드를 바꾸지 않는 확장성이 장점
  • payload와 의미가 바뀌므로 schema version·호환성 규칙이 필요

이벤트에 “누가 무엇을 하라”는 지시를 숨기면 사실 통지와 작업 명령의 경계가 무너집니다.

04 · 예시로 연결하기

예시: 주문 이벤트가 초당 100개 들어오는데 포인트 소비자는 80개만 처리합니다. 미처리 메시지는 매초 20개씩 증가합니다.

또 소비자가 100점을 지급한 직후 완료 확인 전에 종료되면 같은 메시지가 재전달될 수 있습니다.

02 · 핵심 요약

업무 변경과 발행 의도를 함께 저장합니다. 전송은 나중에 복구할 수 있지만 중복 전송까지 저절로 사라지는 것은 아닙니다.

DB 저장과 메시지 발행 사이의 구멍

단순히 저장 후 전송하면 왜 부족한가?

  • 주문을 저장한 뒤 `OrderPlaced` 메시지를 발행한다고 합시다.
  • DB를 먼저 커밋하고 발행하면, 커밋 직후 프로세스가 죽을 때 주문은 존재하지만 메시지는 없습니다.
  • 반대로 메시지를 먼저 발행하면, 메시지를 본 소비자가 일을 시작한 뒤 주문 DB 변경이 롤백될 수 있습니다.
  • 서로 다른 시스템인 DB와 브로커를 단순한 코드 순서만으로 원자적으로 만들 수 없기 때문에 생기는 문제입니다.

아웃박스는 무엇을 함께 남기나?

  • 트랜잭셔널 아웃박스는 업무 데이터와 발행할 메시지를 같은 DB 안에 저장합니다.
  • 두 행은 하나의 로컬 트랜잭션으로 함께 커밋되거나 함께 롤백됩니다.
  • 이후 별도의 relay가 아웃박스 행을 읽어 브로커로 전송합니다.
  • 이로써 “주문은 저장됐지만 발행해야 한다는 사실 자체가 사라지는” 문제를 막습니다.
  1. 주문 행과 고유 event ID를 가진 outbox 행을 같은 트랜잭션에서 작성합니다.
  2. 커밋이 끝나면 사용자의 주문과 발행 의도가 함께 살아남습니다.
  3. relay가 WAITING 행을 가져가 브로커로 발행합니다.
  4. 발행 성공 뒤 DONE으로 표시하거나 마지막 처리 위치를 갱신합니다.
  5. 중간에 죽으면 남은 WAITING 행을 재처리합니다. 발행 성공 직후 죽었다면 중복 발행이 가능하므로 소비자는 멱등해야 합니다.
Outbox가 보장하는 것업무 변경과 발행 의도가 DB에 함께 남는 로컬 원자성
Outbox가 보장하지 않는 것브로커 전송과 DONE 기록 사이의 완전한 exactly-once

폴링 relay와 CDC relay

  • 폴링 방식은 애플리케이션이 일정 간격으로 outbox 테이블을 조회합니다.
  • 이해하고 운영하기 쉽지만 조회 간격만큼 지연이 생기며, 여러 relay가 같은 행을 집지 않도록 잠금 또는 claim 전략이 필요합니다.
  • CDC 방식은 DB의 WAL이나 binlog에서 커밋된 outbox 변경을 읽습니다.
  • 지연을 줄이고 주기적 조회를 피할 수 있지만 커넥터, offset, replication slot, 스키마 변경과 로그 보존을 운영해야 합니다.

CDC는 도메인 이벤트와 같은가?

  • CDC가 관찰하는 기본 사실은 “어떤 테이블의 어떤 행이 바뀌었다”입니다.
  • 반면 `OrderPlaced` 같은 도메인 이벤트는 “업무적으로 주문이 접수됐다”는 의미를 전달합니다.
  • 비밀번호 칼럼이 바뀌었다는 row change만으로 사용자가 비밀번호를 변경했는지 관리자가 초기화했는지 알 수 없는 것처럼, 데이터 변경만으로 업무 의미가 충분하지 않을 수 있습니다.
  • 그래서 도메인 의미를 담은 outbox 행을 CDC로 전달하는 조합이 자주 사용됩니다.

배치 전송

배치는 여러 건을 모아 정해진 시각이나 크기 기준으로 전달합니다. 정산처럼 “다음 날 오전까지”가 계약이라면 건별 실시간 API보다 실패 범위와 운영 시점을 명확하게 통제할 수 있습니다. 실시간보다 열등한 방식이 아니라 요구되는 신선도와 복구 방식이 다른 선택입니다.

  1. 생산자는 특정 시점까지의 레코드를 확정하고 임시 파일에 씁니다.
  2. 건수·합계·checksum 같은 검증 정보를 함께 만듭니다.
  3. 쓰기 완료 뒤 원자적 rename이나 완료 마커로 “완성된 파일”임을 표시합니다.
  4. 소비자는 예약 시각에 파일을 가져와 형식과 검증 값을 확인합니다.
  5. 처리한 파일명 또는 business key를 기록하고 성공 파일은 보관 경로로 이동합니다.

반드시 계약할 것

  • 누가 업로드/다운로드하며 시간대와 마감 시각은 무엇인가
  • 파일명, 문자 인코딩, 구분자, escape, 날짜·금액 형식과 schema version
  • 빈 파일은 “데이터 0건”인지 생성 실패인지
  • 부분 파일·중복 파일·늦은 파일·누락 파일을 어떻게 구별하고 알릴지
  • 재실행 범위와 checkpoint/watermark를 어디에 기록할지

CDC

일반적인 log-based CDC(Change Data Capture)는 애플리케이션 쿼리를 주기적으로 조회하는 대신 DB의 커밋된 변경 로그—PostgreSQL WAL, MySQL binlog 등—를 읽습니다. 처리기는 마지막으로 읽은 위치를 저장하고 INSERT·UPDATE·DELETE 변경을 대상 DB나 메시지 브로커에 전달합니다.

  1. 기존 데이터가 필요하면 초기 snapshot을 만들고 그동안의 로그 위치를 연결합니다.
  2. 커밋된 변경을 순서대로 읽어 row key, 변경 전후 값, 연산 종류를 change record로 만듭니다.
  3. 대상에 전달한 뒤 offset/LSN을 안전하게 갱신합니다.
  4. 재시작하면 저장한 위치부터 다시 읽습니다. 경계에서 중복이 생길 수 있으므로 대상 반영도 멱등해야 합니다.

도입하면 새로 운영할 것

  • offset 유실·초기 snapshot과 이후 change stream 연결
  • 스키마 변경, 테이블 rename, 삭제와 tombstone 의미
  • 복제 슬롯·로그 보존·커넥터 지연 때문에 DB 로그가 쌓이는 문제
  • 민감 칼럼이 변경 로그와 여러 소비자로 확산되지 않도록 하는 통제
  • CDC row change를 업무 의미가 있는 도메인 이벤트로 변환할 책임
보장 범위 주의DB에서 커밋 순서로 읽는 것과 모든 토픽·소비자·대상 시스템에서 전역 exactly-once가 성립하는 것은 다릅니다.

  2. 예측 조작하기 전에 “B가 느려지면 어떤 숫자가 먼저 늘까?”처럼 결과를 먼저 말합니다.
  3. 실험 슬라이더와 장애 버튼을 하나씩 바꾸고, 설명 문장의 원인과 결과를 다시 연결합니다.
  4. 설명 교대 한 사람은 장애를 만들고 다른 사람은 점유 자원, 사용자 결과, 복구 책임을 1분 안에 설명합니다.
  5. 실습 연결 마지막에는 같은 현상을 실제 Spring 서비스의 metric·로그·DB 상태로 관찰합니다.

정답의 기준은 패턴 이름을 많이 말하는 것이 아니라 “실패했을 때 무엇이 남고, 누가 다시 처리하며, 중복을 어떻게 막는가”를 끝까지 설명하는 것입니다.

4장 확인

  1. B 지연이 왜 A의 스레드와 HTTP 풀을 포화시키는가?
  2. 읽기 타임아웃 뒤 B가 성공했을 가능성은 어떻게 다룰까?
  3. 재시도, 동시성 제한, 벌크헤드, 서킷 브레이커는 각각 무엇을 보호할까?
  4. 풀을 크게 하면 처리량이 반드시 늘지 않는 이유는?

5장 확인

  1. 별도 스레드와 메시지 브로커는 작업 보존 측면에서 어떻게 다른가?

  3. 아웃박스를 사용해도 중복 발행 가능성이 남는 이유는?
