# 4·5장 두 사람 실습 커리큘럼

이 실습의 목표는 패턴 이름을 외우는 것이 아니라 **응답·실제 저장·미완료 작업·사용 자원을 따로 관찰하고, 어떤 실패에 어떤 해결을 적용할지 설명하는 것**이다.

## 두 사람의 역할

- 실행자: 상황·읽기용 코드를 설명하고, 두 사람의 예측을 입력한 뒤 버튼을 누른다. 실험 중 터미널은 필요 없다.
- 관찰자: 같은 Wi-Fi의 관찰 페이지에서 값이 바뀌는 것을 보고 “무엇이 실제로 끝났는가”를 설명한다.
- 결과: 응답만 보지 않고 DB·큐·파일·로그 위치 같은 증거와 대조한다. 서로의 예측이 왜 맞거나 틀렸는지 한 문장으로 남긴다.
- 역할을 주제별로 바꿔도 된다. 관찰 페이지에서는 명령 실행·초기화를 할 수 없다.

## 전체 이야기

1. A가 B를 기다리다가 느려진다 → 연결과 대기 자원을 관리한다.
2. A가 오류를 받았는데 B는 성공했다 → 재시도 전에 멱등성을 만든다.
3. 사용자에게 빨리 응답하고 싶다 → 비동기로 분리하되 할 일을 잃지 않게 한다.
4. B가 멈춰도 나중에 처리하고 싶다 → 아웃박스·브로커·ACK로 전달과 처리를 구분한다.
5. 모든 일을 즉시 처리할 필요는 없다 → 배치나 CDC가 맞는 연동을 구분한다.
6. B가 장기간 안 되면 다른 곳으로 보내고 싶다 → 미처리 확정과 결과 불명을 구분하며 이중화한다.

아래 결과는 **확인할 기준**이며 실제 측정값이 아니다. 실행 페이지는 버튼으로 얻은 값을 별도로 기록한다.

## A. 동기 연동을 보호한다 — 1~14단계

| 단계 | 하는 일 | 이 단계의 의미·관찰 기준 |
| --- | --- | --- |
| 1 준비 | A·B·큐·풀 설정과 남은 작업 확인 | 이전 장애가 이번 결과에 섞이지 않게 한다. 설정 준비도 완료 근거가 있어야 한다. |
| 2 연결 닫기 | 정상 요청 3회를 `Connection: close`로 전송 | 요청과 TCP 연결은 같은 단위가 아니다. B 로그의 remote 포트를 본다. |
| 3 연결 재사용 | 같은 수의 요청을 같은 HTTP 풀로 전송 | 연결 재사용과 응답 캐시는 다르다. 풀 2개가 미리 요청 2개를 만든다는 뜻도 아니다. |
| 4 느린 B | 저장 전 지연 3초, 작성 24건·별도 조회 12건 | HTTP 대기 때문에 DB 연결까지 붙잡히는 구조를 본다. A의 타임아웃은 B의 작업 취소가 아니다. |
| 5 DB 경계 분리 | 같은 부하로 외부 호출을 DB 트랜잭션 밖으로 이동 | B는 그대로 느려도 DB 점유가 줄 수 있다. 원격 성공 후 로컬 실패의 불일치는 남는다. |
| 6 동시 요청 제한 | 5단계에 세마포어 2개 추가 | HTTP 풀 앞에 대기를 계속 쌓지 않고 초과 요청을 빠르게 거절한다. 자원 보호는 성공 보장이 아니다. |
| 7 회로 없음 | B가 503인 동안 6회 순차 호출 | 동시 요청 제한만으로 반복되는 헛호출을 막지 못한다. 실제 B 수신 6회를 확인한다. |
| 8 회로 차단 | 같은 조건에 연속 실패 3회 차단 추가 | 6회 모두 실패해도 B 호출은 3회로 줄 수 있다. OPEN은 오류를 성공으로 바꾸는 상태가 아니다. |
| 9 회복 시험 | B 정상화, 3초 경과, 시험 요청 | HALF_OPEN에서 실제 시험 후 CLOSED로 돌아온다. 중간 상태를 직접 조회한 증거도 남긴다. |
| 10 조건 복구 | B 정상화·남은 작업 확인 | 다음 타임아웃 실험의 출발 조건이다. DB 삭제나 새로운 성능 측정 단계가 아니다. |
| 11 응답 유실 | B는 지급하고 응답만 3초 지연 | A는 실패·리뷰 롤백, B 지급은 성공할 수 있다. 응답 오류와 업무 실패를 분리한다. |
| 12 단순 재시도 | 11단계 같은 업무 ID 재전송 | 리뷰 1건이어도 지급은 2건이 될 수 있다. 재시도는 항상 안전하지 않다. |
| 13 멱등 처리 | 새 ID로 응답 유실·재시도를 반복하되 UNIQUE 업무 키 사용 | 여러 요청에도 지급 효과 1회. 조회 후 INSERT 대신 원자적인 DB 제약으로 동시 중복도 막는다. |
| 14 백오프 | 1.2초 장애에 즉시 3회와 간격 있는 최대 3회 비교 | 횟수가 같아도 시점이 다르면 회복 후 성공 가능성이 다르다. 무한 재시도·지터·오류 분류는 추가 과제다. |

토론: **“5단계에서 HTTP 오류는 그대로인데 DB 점유가 줄었다면, 개선에 실패한 것인가?”**

## B. 비동기 작업을 잃지 않는다 — 15~20단계

| 단계 | 하는 일 | 이 단계의 의미·관찰 기준 |
| --- | --- | --- |
| 15 메모리 비동기 | 리뷰 저장 후 메모리 작업자를 일시정지 | 응답이 빨라도 지급은 미완료다. 리뷰 1·지급 0·메모리 작업 대기를 본다. |
| 16 A 종료 | 확인 후 A만 강제 종료·재시작 | 리뷰는 DB에 남지만 메모리의 할 일은 사라진다. 별도 스레드만으로 내구성을 얻지 못한다. |
| 17 아웃박스 저장 | 리뷰와 지급할 일을 같은 DB 트랜잭션으로 저장 | 리뷰 1·지급 0·WAITING 1. 응답 시점에 할 일까지 안전하게 접수했는지 본다. |
| 18 A 복구 | 확인 후 A 재시작, 이번 세션 전달자 재개 | WAITING이 살아 있고 결국 DONE·지급 1로 바뀐다. 전달 후 상태 기록 전 실패 때문에 멱등 수신도 필요하다. |
| 19 큐 적체 | B 소비자를 멈추고 실제 RabbitMQ로 3건 전달 | 리뷰 3·outbox DONE 3이지만 지급 0·큐 3. 생산자 확인과 소비자 완료는 다르다. |
| 20 큐 소비 | 소비 재개, 지급 커밋 후 ACK | 지급 3·큐 0을 확인한다. 커밋 후 ACK 전 종료라면 재전달될 수 있으므로 멱등 처리가 필요하다. |

토론: **“아웃박스 DONE인데 포인트가 0이라면 반드시 버그인가? 전달 대상이 HTTP인지 브로커인지에 따라 의미가 어떻게 다른가?”**

## C. 연동 방식과 대체 경로를 선택한다 — 21~30단계

배치·CDC는 지급 실험과 혼동하지 않도록 별도의 복제 데이터를 사용하고 전용 증거 카드를 표시한다.

| 단계 | 하는 일 | 이 단계의 의미·관찰 기준 |
| --- | --- | --- |
| 21 배치 대기 | 원본 리뷰 3건 저장, 전송은 아직 안 함 | 원본 3·수신 0은 의도된 시간차다. 즉시성이 필요하지 않은 업무에는 주기 전송이 가능하다. |
| 22 배치 부분 실패 | 실제 JSONL·manifest 생성, 첫 행 커밋 뒤 중단 | 파일 3건인데 수신은 1건이다. 파일 수신·검증과 전체 업무 완료를 구분한다. |
| 23 배치 재처리 | 같은 파일 검증·재실행, 업무 키 중복 방지 | 신규 2·수신 총 3. 파일과 멱등 반영 규칙이 있으면 부분 실패를 복구할 수 있다. |
| 24 CDC 지연 | 슬롯 생성, 원본 INSERT·UPDATE·DELETE·ROLLBACK, WAL peek | 최종 원본 1행이지만 커밋 변경은 4개. 롤백 ID는 없다. 현재 상태 조회와 변경 로그는 다르다. |
| 25 CDC 확인 전 중단 | 변경 4개 반영, 슬롯 위치 확인은 생략 | 원본·대상은 같아도 재개 시 같은 변경을 받을 수 있다. 대상 커밋과 원본 위치는 별개다. |
| 26 CDC 재개 | 새 호출로 재수신, 중복 4개 건너뛰고 위치 확인 | 신규 적용 0·대상 유지·진행 위치 갱신. 끝에 이번 슬롯만 정리해 WAL 보관을 종료한다. |
| 27 단일 제공자 | B가 미처리 확정 거절, 단일 경로 호출 | REJECTED·주 0·대체 0. B2가 켜져 있어도 경로가 없으면 업무는 멈춘다. |
| 28 대체 제공자 | 미처리 확정 계약 확인 후 B2로 실제 HTTP 호출 | 주 0·대체 1·100포인트. 서킷은 차단, 페일오버는 다른 수행 경로 제공이다. |
| 29 불명 결과 | B 지급 후 응답 지연; 무조건 전환과 UNKNOWN 보류 비교 | 위험한 전환은 주 1+대체 1=200, 보류는 주 1+대체 0=100. 제공자별 멱등 키로 제공자 간 중복을 막지는 못한다. |
| 30 결과 조회 | 앞 safe ID로 주 제공자 장부 조회, 새 지급 안 함 | 100포인트 유지. UNKNOWN을 실패로 단정하지 않고 기존 성공을 확인한다. |

토론: **“B가 타임아웃일 때 B2를 호출해도 되는가?”** 답은 타임아웃 자체가 아니라 **B가 처리했는지 확정할 수 있는 계약·조회·대사 방법**에 달려 있다.

## D. 마무리 — 31단계

주·대체 제공자의 장애 설정을 정상화하고 A 작업자를 풀어 준다. 아웃박스 전달자·메시지 소비자는 정지한다. 이번 세션의 남은 CDC 슬롯은 종료한다. **DB 행·배치 파일·예측·결과를 삭제하지 않는다.** 전체 데이터 초기화는 별도 동의 버튼이다.

## 교재와 실습의 범위

- 4장 핵심: 타임아웃, 재시도·멱등성, 동시 제한, 서킷, DB 트랜잭션/풀, HTTP 풀, 연동 이중화를 실제 사례로 다룬다.
- 5장 핵심: 스레드 비동기, 메시징, 아웃박스, 배치, CDC를 실제 코드와 저장 결과로 다룬다.
- 모든 단락이 독립된 실험이라는 뜻은 아니다. 커맨드/이벤트, 지터, CDC 업무 의미 손실, DLQ·운영 경보 등은 설명/확장 질문으로 구분한다.
- 배치의 정시 스케줄·SFTP, CDC의 Debezium·초기 스냅샷·DDL·다중 소비자, 이중화의 독립 DB/리전·자동 보상·자동 대사 스케줄러는 구현하지 않는다.
- B2는 다른 프로세스와 다른 지급 장부지만 같은 노트북·DB를 공유한다. 제공자 호출 실패를 실험하는 것이며 DB나 노트북 장애 내성을 입증하지 않는다.
- CDC는 실제 WAL을 사용하지만 25단계의 중단은 위치 확인을 생략하는 실패 지점 주입이다. 프로세스 강제 종료는 16·18단계에서 실제 수행한다.
- 예약된 작은 부하 실험은 최대 처리량 벤치마크가 아니다. 표본 사이 최대값을 놓칠 수 있고 로컬 CPU·수집 부하가 영향을 준다.

## 쉬었다 이어갈 때

주제 묶음 사이에 쉬어도 된다. 단, 현재 서버는 UI 세션 재시작 복원을 지원하지 않는다. 브라우저 새로고침은 괜찮지만 화면 서버를 종료하면 다음에는 새 세션이다. 오래 쉴 때는 기록을 내려받고 마무리를 실행한다. CDC 중간에는 슬롯을 반드시 종료한다. 지난 DB와 `runs` 기록은 그대로 남는다.
